# A2A 系统问题与改进清单

本文整理 A2MCP、A2A 单次和 A2A 订阅的当前问题、风险与改进事项，用于产品、研发和测试统一排期。

> 结论基于当前 Skill、Reference 和 CLI 实现审查。耗时、转化率和故障率仍需通过真实链路埋点验证。

## 1. 当前判断

三条链路的目标不同，不应使用同一种交互和授权强度：

| 链路 | 用户目标 | 设计重点 |
|---|---|---|
| A2MCP | 快速调用一次服务并获得同步结果 | 少步骤、支付与响应可追踪 |
| A2A 单次 | 委托一次任务并等待交付 | 状态清晰、异步可靠、验收可恢复 |
| A2A 订阅 | 持续接收周期性服务 | 周期扣费、消息可靠、长期可控 |

当前主要矛盾：

1. 状态、事件、Runtime 和恢复规则分散，正确性依赖大量 Prompt 约束。
2. 内部检查和 CLI 步骤容易透传给用户，正常流程偏长。
3. 本地构建、依赖、调试、事件模拟和真实环境验证成本高。
4. 支付、订阅、接收和自动执行的授权边界容易混淆。
5. 订阅基础能力尚未完全稳定，自动跟单又进一步放大复杂度与风险。

## 2. 已发现的问题

### 2.1 系统基础

- 后端状态与 XMTP/Watch 事件缺少统一的处理契约。
- 旧事件、重复事件和乱序事件可能推动重复操作。
- 写入超时后难以区分“未执行”和“已执行但回执丢失”。
- 创建任务、创建订阅、支付、验收等操作的幂等依据不统一。
- Runtime 支持矩阵分散在多个 Reference，存在能力描述不一致的风险。
- Watch、原生 XMTP 和不支持场景之间的降级策略不够统一。
- 部分流程仍依赖对话上下文判断是否处理过消息。
- 缺少统一任务链路追踪，难以回答事件、状态、动作和结果之间的关系。

### 2.2 安全

- Provider 的 Guide、描述、消息和交付物可能影响模型决策，但它们不应提供执行权限。
- 订阅服务容易被误解为同时授权自动执行或自动交易。
- 支付授权、订阅授权、接收策略和执行授权没有完全独立。
- 历史授权可能被错误复用于新服务、新任务或新设备。
- 自动执行失败后的重试边界不够直观。
- A2MCP Endpoint 可能发生域名替换、跨域重定向或服务内容变化。
- 付款成功但 Endpoint 超时时，可能被误判为付款失败并再次支付。
- 多设备接收中 `null`、空列表等内部语义容易导致误配置。

### 2.3 本地开发与测试

- Cargo 缓存权限、Node 版本、CLI 路径和本地配置容易混淆。
- 本地 debug binary 与全局 CLI 可能不是同一个可执行文件。
- `ONCHAINOS_HOME`、Base URL、feature flag 等参数需要手工组合。
- 缺少一条命令完成环境准备、构建、运行和测试。
- 缺少稳定的测试 Agent、Service、Task 和 Subscription fixtures。
- 缺少事件重放工具，难以复现重复、乱序、超时和中断恢复。
- 基础测试过度依赖真实后端、真实身份或真实支付。
- 日志缺少统一 `traceId/jobId/eventId/statusBefore/statusAfter` 上下文。
- 全链路测试文件和现有 Reference 之间可能出现路径或契约漂移。

### 2.4 产品流程与用户体验

- 登录、身份、余额、服务、Runtime 和通信检查可能逐步暴露给用户。
- 参数可能逐项收集，交互轮次过多。
- A2A 单次中的“ASP 申请”“用户确认 ASP”“任务正式开始”容易混淆。
- 等待接单、等待交付、等待验收时缺少统一时间线和剩余时间。
- 用户需要理解过多内部概念，例如 `jobId`、Watch、XMTP 和 CLI。
- 失败后恢复入口分散，用户不知道应该重试、查询还是等待。
- 多设备环境下，用户不知道哪个设备会接收消息。
- 订阅卡片没有始终完整表达当前周期、已付金额、续费状态和下次扣费时间。
- A2MCP 如果走完整任务式前置流程，会失去即时 API 的体验。

### 2.5 产品功能完整性

- A2A 单次后半程的新状态推进机制仍需完整接通真实 XMTP 事件。
- 缺参数信号、字段列表和回复机制尚需统一协议。
- 订阅创建、试用、周期扣费、续费、取消和当前周期语义需要完整验证。
- 订阅消息的接收、持久化、确认、离线恢复和乱序处理仍需收口。
- 周期拒收、退款、仲裁和 ASP 收款需要完整端到端测试。
- 订阅恢复监听和设备策略需要统一产品入口。
- 自动跟单仍涉及信号解析、工具路由、交易授权和结果回传等未完全稳定能力。

## 3. 优先级

### P0：系统正确与资金安全

| TODO | 产出 | 验收标准 |
|---|---|---|
| 统一任务与订阅状态模型 | 状态、终态、允许动作表 | 任意阶段只有明确允许动作 |
| 统一事件协议 | `eventId/jobId/deliveryId/role/status` 契约 | 重放和乱序不会重复执行 |
| 建立写入幂等 | 各写操作幂等键和查询方式 | 超时后不会重复创建或支付 |
| 状态新鲜度校验 | 写前和事件处理前查询状态 | 过期事件返回 `stale_event` |
| 拆分授权模型 | 支付、订阅、接收、执行四类授权 | 任一授权不能推导其他授权 |
| 收口 Runtime 能力 | 唯一 Capability Matrix | 所有 Reference 引用同一结论 |
| 固化不可信数据边界 | Provider 数据处理规范 | Provider 文本不能直接触发写入 |

P0 完成前，不扩大自动执行范围。

### P1：开发效率与可验证性

| TODO | 产出 | 验收标准 |
|---|---|---|
| 一键本地环境 | `dev setup/build/run/test/debug` | 新开发者按文档一次启动成功 |
| 统一项目内配置 | 本地 Cargo、Node、Home、Base URL 默认值 | 不依赖修改全局环境 |
| 事件模拟与重放 | 事件 fixture 和 replay 命令 | 可复现重复、乱序、超时、中断 |
| A2A 单次基准 E2E | 正常与异常测试集 | 创建到终态全部自动验证 |
| 统一链路日志 | trace、状态、动作、耗时字段 | 可按 jobId 还原完整过程 |
| 契约测试 | Skill/Reference/CLI 字段一致性检查 | 文件或字段漂移在 CI 中失败 |

### P2：用户流程简化

| TODO | 目标 |
|---|---|
| 并行 Preflight | 一次返回登录、身份、余额、服务和 Runtime 问题 |
| 参数批量收集 | 一次展示所有必填、可选和影响价格的字段 |
| A2MCP 快速路径 | 选择、一次确认、支付调用、返回结果 |
| A2A 单次三次决策 | 创建任务、确认 ASP、验收交付物 |
| 统一任务时间线 | 当前状态、责任人、截止时间、超时后果、下一步 |
| 统一任务中心 | 待我处理、等待对方、执行中、订阅中、已结束、异常 |
| 统一恢复入口 | 明确查询、重试、恢复监听和停止操作 |
| 隐藏内部实现 | 不要求用户理解 jobId、CLI、Watch 或 XMTP |

### P3：订阅与自动执行

先完成纯订阅，再推进自动跟单。

#### P3-A：纯订阅

- 创建、试用、首期扣费和周期续费。
- 关闭自动续费但保留当前周期。
- 重复订阅保护。
- 消息接收、落盘、确认和离线恢复。
- 多设备选择和禁用接收确认。
- 周期拒收、退款、仲裁和 ASP 收款。
- 订阅详情、月度费用和价值摘要。

#### P3-B：自动执行

按风险逐级开放：

```text
只接收
→ 每次确认后执行
→ Demo 自动执行
→ 小额 Live 自动执行
→ 完整策略
```

每一级独立验收，不因订阅成功自动升级执行权限。

## 4. 推荐实施顺序

```text
阶段 1：统一状态、事件、幂等、授权和 Runtime
阶段 2：一键开发环境、事件回放、日志和契约测试
阶段 3：跑通 A2A 单次正常与异常全生命周期
阶段 4：简化 A2MCP 和 A2A 单次用户流程
阶段 5：完成纯订阅生命周期
阶段 6：分级开放自动执行
```

当前建议的唯一主线目标：

> 先让 A2A 单次在统一状态、统一事件、统一授权和可重复的本地环境下稳定跑通，再复用相同基础扩展订阅；自动跟单最后独立验收。

## 5. 关键指标

| 指标 | 目的 |
|---|---|
| 首次结果耗时 | 衡量 A2MCP 的即时体验 |
| 首次价值耗时 | 衡量首次交付或首条订阅信号速度 |
| 用户决策次数 | 判断流程是否过长 |
| 正常链路 CLI 调用次数 | 判断内部复杂度 |
| 各阶段放弃率 | 定位体验阻塞点 |
| 重复创建/支付率 | 衡量幂等有效性 |
| 事件处理延迟 | 衡量通知体验 |
| 重复和乱序事件率 | 衡量通信可靠性 |
| 中断恢复成功率 | 衡量可恢复性 |
| 超时退款率 | 衡量 ASP 履约情况 |
| 拒收与争议率 | 衡量任务质量 |
| 订阅留存率 | 衡量持续价值 |
| 订阅交付消费率 | 衡量用户是否真正使用交付内容 |

## 6. 暂不建议做的事

- 在状态和事件模型未收口前继续增加新的流程分支。
- 在纯订阅未稳定前扩大自动跟单能力。
- 用更多 Prompt 规则代替幂等、状态机和服务端事件处理。
- 为不同 Runtime 分别维护一套业务流程。
- 只验证正常演示路径，跳过重复、乱序、超时和恢复。
- 将内部 CLI、Watch 和通信细节直接暴露给用户。
